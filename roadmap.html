GPU 编程、分布式训练与推理系统

课程目标

路线按知识依赖排列。前四个阶段学习计算量、显存和 GPU 编程，随后学习通信与训练并行。推理部分以一次生成请求为例，讨论模型状态、调度和服务容量。

总目标
给定模型配置和工作负载，估算 FLOPs、显存和通信量。用这些估算选择并行布局，解释 TTFT 或 TPOT 的变化，并核算改用稀疏注意力或递归状态后的成本。
↑ 返回知识点目录

计算、访存、通信与调度

• Compute：算多少 FLOPs、Tensor Core 利用率多少、是否被非 GEMM 运算拖慢。

• Memory：权重、激活、optimizer state、KV cache 占多少；HBM↔SRAM/DRAM/SSD 搬多少字节。

• Communication：collective / P2P / RDMA 搬多少，走哪条 topology，能否与计算 overlap。

• Scheduling：训练的 bubble/straggler，推理的 queue/batch/cache locality，以及 SLO 下的 goodput。

硬件、模型与框架

• 分块算子有多种实现，包括 CuTeDSL、cuTile、TileLang 和 ThunderKittens。FlashAttention-4 可用来比较矩阵乘、softmax 与数据搬运在 Blackwell 上的分工。

• NCCL 同时提供主机发起的集合通信与设备侧接口。GIN、CFT 和对称内存各有不同的寻址方式与完成条件。

• TorchTitan 用配置描述分片，在多个并行维度上使用 DTensor。阅读 spmd_types 时，区分存储布局和算子执行时的张量约束。

• 百万 token 的状态容量取决于每层保留的信息。稀疏索引改变读取位置，线性注意力维护递归状态，KV 量化改变每条记录的字节数。

• 分离式推理需要跨机交接 KV。NIXL、Mooncake 与 Dynamo 分别涉及传输、缓存或路由，阅读时要确认各组件负责的操作。

• 智能体训练同时涉及采样、工具等待和策略更新。部分轨迹跨越权重切换时，还要记录行为策略的版本。

张量形状与计算量

• 从 shape 推导 QKV、attention、MLP 的矩阵乘；区分训练 FLOPs、单 token decode FLOPs、prefill FLOPs。

• 参数显存、梯度、optimizer state、activation、KV cache 的数量级；知道 MHA/MQA/GQA/MLA 为什么改变 KV 成本。

• Roofline：arithmetic intensity、peak compute、HBM bandwidth；识别 compute-bound / memory-bound / latency-bound。

• 指标：TFLOP/s、MFU/HFU、tokens/s、TTFT、TPOT/ITL、E2E latency、goodput、SLO attainment。

AMD GPU、TPU 与 Trainium

官方 AMD Instinct MI355X / CDNA4 — 288GB HBM3E、8TB/s、MXFP4/MXFP6。

编程练习顺序

• CUDA 练习依次实现向量加法、归约、分块 GEMM 和 softmax。逐步检查相邻线程的访存地址、共享内存复用、warp 内交换以及异步拷贝的完成条件。

• Triton：同样做 vector add / fused softmax / matmul；理解 program instance、block pointer、autotune。

• CuTe/CUTLASS：理解 layout algebra、MMA pipeline 与新架构特性如何暴露。

• 用 cuTile、TileLang 和 ThunderKittens 实现分块计算，比较 tile 布局、流水线和同步的写法。

• 模型定制 kernel：DeepGEMM。它已经覆盖 FP8/FP4/BF16 GEMM、Mega MoE、sparse indexer、mHC，并通过 DeepJIT runtime 编译。

阶段 5　集合通信与 RDMA

模型扩到多卡后，先按通信组计算需要传输的字节，再标出链路和数据依赖。只有当计算可以独立推进且资源足够时，通信才有机会被覆盖。

集合通信原语

• 必须手推：Broadcast、AllReduce、ReduceScatter、AllGather、AllToAll；Ring vs Tree；alpha-beta latency/bandwidth model。

• 训练映射：DDP→AllReduce；FSDP→AllGather+ReduceScatter；TP→AllReduce/AllGather/ReduceScatter；MoE EP→AllToAll。

DeepSeek V4.1 必须真正理解的 6 件事

百万上下文 MoE 平台设计

不要选择多个 capstone。就做这一个：假设你要部署一个 1M context、MoE、原生 multimodal 的 Agent 服务，同时支持在线 inference 和持续 RL post-training。你可以用较小开源模型做实验，但设计必须按 frontier scale 写。

• 模型层：说明 attention/KV 方案（例如 GQA/MLA/sparse/linear hybrid）、MoE routing、precision、speculative decoding。

• 训练层：DP/TP/PP/CP/EP mesh、activation strategy、optimizer/precision、checkpoint、data path。

• 通信层：节点内/节点间 collective、EP all-to-all、GPU-initiated / RDMA 的候选路径。

• Serving 层：vLLM/SGLang engine，continuous batching、chunked prefill、prefix cache；是否 P/D 分离以及为什么。

• KV 层：HBM/DRAM/NVMe/remote pool 容量；KV-aware routing；压缩与持久化；cache admission/eviction。

• RL 层：rollout/trainer 是否 colocate，async queue、tool long-tail、weight transfer、staleness 控制。

• 平台层：Slurm/K8s、gang/topology scheduling、storage、observability、fault recovery、cost model。

• 评测：训练 tokens/s/MFU；推理 TTFT/TPOT/goodput；cache hit；network bytes/token；$/task；故障恢复时间。

论文与源码阅读

以后遇到任何新 AI Infra 技术，固定用下面七问，不要重新建立一套名词体系：

• 它在优化哪一个资源：FLOPs、HBM bytes、KV capacity、network bytes、latency、launch overhead、storage I/O？

• 瓶颈发生在训练还是 inference？prefill 还是 decode？短 context 还是长 context？dense 还是 MoE？

• 它把成本转移到哪里？例如 sparse attention 是否把成本转移给 indexer；P/D 是否把成本转移给 KV transfer；activation offload 是否把成本转移给 PCIe。

• 它依赖什么硬件假设：HBM/Tensor Core 比、NVLink domain、RDMA、FP4、TMA、symmetric memory？

• 它改变了 tensor layout / parallel mesh / scheduler 的哪一部分？

• 它的核心 benchmark 是否匹配真实 workload distribution 和 SLO，而不只是 microbenchmark？

• 如果换一代硬件（Hopper→Blackwell→Rubin，或 NVIDIA→AMD/TPU），这个优化还成立吗？
