从 GPU / Kernel 到万卡训练、百万上下文、分布式推理与 Agentic RL

技术截止日期：2026 年 9 月 21 日

一条路线 · 顺序学习 · 论文 / 官方文档 / 框架 / 实战 / 掌握标准

0｜这份文档解决什么问题

先建立计算、内存与通信的成本模型，再读单机算子、分布式训练、长上下文模型和推理服务。最后用同一组工具分析强化学习训练、集群恢复与容量成本。各阶段的检查点可以用来决定从哪一课开始。

总目标
完成后，你应该能从一个模型结构或 workload 出发，估算 FLOPs、HBM/KV 占用和通信量；选择并组合 DP/TP/PP/CP/EP；定位 kernel/网络/调度瓶颈；设计满足 TTFT/TPOT/SLO 的 Serving；并读懂 DeepSeek V4.1、Kimi K3、Qwen3.8-Flash-Next 这类 2026 架构为何这样设计。

贯穿全程的四个成本模型

• Compute：算多少 FLOPs、Tensor Core 利用率多少、是否被非 GEMM 运算拖慢。

• Memory：权重、激活、optimizer state、KV cache 占多少；HBM↔SRAM/DRAM/SSD 搬多少字节。

• Communication：collective / P2P / RDMA 搬多少，走哪条 topology，能否与计算 overlap。

• Scheduling：训练的 bubble/straggler，推理的 queue/batch/cache locality，以及 SLO 下的 goodput。

2026-09-21 的变化：为什么旧路线不够了

• Kernel 编程从“CUDA 或 Triton”扩展到 CuTeDSL、cuTile、TileLang、ThunderKittens、DeepGEMM；FlashAttention-4 已针对 Blackwell 的非对称硬件 scaling 重做 pipeline。

• 通信从 host-launched NCCL collective，继续向 symmetric memory、GPU-initiated networking、NCCL Device API / GIN / CFT、DeepEP/MoonEP 等计算-通信融合方向发展。

• 分布式训练抽象正在从“手写 parallelize_module”继续向 DTensor + declarative sharding + SPMD contracts 发展；TorchTitan 在 2026 年采用 config-based sharding 和 spmd_types。

• 长上下文不再只是 RoPE scaling：DSA/CSA/QSA 等 learned sparse indexing、KDA/Gated DeltaNet 等线性状态、跨层 residual/memory，以及 KV quantization/持久化共同决定百万 token 成本。

• 推理系统已从“continuous batching + PagedAttention”走到 KV fabric：P/D disaggregation、KV-aware routing、DRAM/NVMe/remote KV pool、NIXL/Mooncake、Dynamo。

• Agentic RL 使 rollout 成为分布式在线服务问题：异步采样、partial rollout、weight transfer、tool/environment long-tail 与训练 staleness 必须一起处理。

阶段 1｜Transformer 与性能成本模型

第 1–2 周先学会“算账”，否则后面所有优化都只是框架记忆。
↑ 返回知识点目录

你要掌握

• 从 shape 推导 QKV、attention、MLP 的矩阵乘；区分训练 FLOPs、单 token decode FLOPs、prefill FLOPs。

• 参数显存、梯度、optimizer state、activation、KV cache 的数量级；知道 MHA/MQA/GQA/MLA 为什么改变 KV 成本。

• Roofline：arithmetic intensity、peak compute、HBM bandwidth；识别 compute-bound / memory-bound / latency-bound。

• 指标：TFLOP/s、MFU/HFU、tokens/s、TTFT、TPOT/ITL、E2E latency、goodput、SLO attainment。

↑ 返回知识点目录

必读

论文 Attention Is All You Need — 只读结构与计算图，自己推 shape。

论文 Roofline: An Insightful Visual Performance Model — 后续所有 kernel 性能分析的统一语言。

参考 Transformer FLOPs / scaling 的经典估算：Megatron-LM — 先建立训练吞吐与模型规模的数量级感。

↑ 返回知识点目录

实战

• 写一个 Python notebook：输入 hidden size、layers、heads、seq、batch、dtype，输出参数量、训练显存粗算、KV bytes/token、attention/MLP FLOPs。

• 对 Llama-like 7B、70B 和一个 MoE 配置各算一次；再把 context 从 8K 拉到 1M，观察 attention/KV 的增长。

□ 能解释为什么 decode 往往 memory-bandwidth-bound，而长 prefill 更容易 compute-bound。

阶段 2｜GPU、内存层级与 2026 加速器

第 3–4 周理解“硬件为什么长成这样”，才能理解 kernel、精度和通信设计。

核心概念

• SIMT、warp/CTA、SM、register、shared memory、L2、HBM；Tensor Core/MMA；occupancy 与 latency hiding。

• Scale-up 与 scale-out：PCIe、NVLink/NVSwitch、InfiniBand/RoCE；CPU/GPU coherent link 与 NIC。

• 现代硬件越来越“算力涨得比带宽/特殊函数快”：这正是 FlashAttention-4、低精度、fusion 与数据搬运优化越来越重要的原因。

横向看一遍：不要把 AI Infra 等同于 CUDA

官方 AMD Instinct MI355X / CDNA4 — 288GB HBM3E、8TB/s、MXFP4/MXFP6。

官方 Google TPU7x (Ironwood) — 192GiB HBM、7.38TB/s、3D torus、最多 9216 chips。

官方 AWS Trainium2 Architecture — NeuronCore、SBUF、NeuronLink；理解另一种 compiler-first accelerator。

2026 观察
Rubin 的 HBM4 与 NVLink 6、Ironwood 的 3D torus、MI355X 的 MXFP4，都在说明同一件事：AI Infra 的性能边界已经从“单芯片峰值 FLOPs”转向 compute + memory + fabric + precision 的系统共同设计。
↑ 返回知识点目录

实战与掌握标准

• 用 nvidia-smi topo / Nsight 查看一台多 GPU 机器的 topology；画出 GPU↔GPU、GPU↔NIC、GPU↔CPU 数据路径。

□ 能解释 HBM、L2、shared memory、register 的容量/带宽/可编程性差异，以及 tiling 为什么有效。

□ 能解释 scale-up fabric 与 scale-out network 为什么会影响 TP、EP 和 P/D disaggregation 的选择。

阶段 3｜CUDA → Triton → Tile DSL 与高性能 Kernel

第 5–8 周从“会调用算子”升级到能理解和修改热点 kernel。
↑ 返回知识点目录

学习顺序

• CUDA 练习依次实现向量加法、归约、分块 GEMM 和 softmax。逐步检查相邻线程的访存地址、共享内存复用、warp 内交换以及异步拷贝的完成条件。

• Triton：同样做 vector add / fused softmax / matmul；理解 program instance、block pointer、autotune。

• CuTe/CUTLASS：理解 layout algebra、MMA pipeline 与新架构特性如何暴露。

• 2026 tile DSL：cuTile、TileLang、ThunderKittens。目标是看懂“tile-first 编程模型”为何在 Blackwell/Rubin 时代更重要。

• 模型定制 kernel：DeepGEMM。它已经覆盖 FP8/FP4/BF16 GEMM、Mega MoE、sparse indexer、mHC，并通过 DeepJIT runtime 编译。

↑ 返回知识点目录

必读 / 必做

教程 Triton: Matrix Multiplication — 必须亲手敲。

官方 cuTile Python — 2025-12 首发，2026-09 的 1.6 已支持 Rubin FP4 block-scaled MMA 等特性。

项目 TileLang — CUDA/ROCm/Metal 多后端，含 DeepSeek V4、sparse attention、GDN 等例子。

项目 ThunderKittens — tile primitives；2026 支持 Blackwell 与 Rubin。

项目 DeepGEMM — 把现代 LLM 热点 kernel 当作源码教材。

2026-09 重点
cuTile 1.6（2026-09-09）加入 Rubin FP4 block-scaled MMA 等 CUDA 13.4 能力；DeepGEMM 2026-09-10 更新 sparse indexer / Mega Gate / Mega mHC；ThunderKittens 2026-09-10 加入 Vera Rubin 支持。不要把这些当成三个新框架去背，而要比较它们怎样表达 tile、pipeline、layout 和低精度 MMA。
↑ 返回知识点目录

实战

• 同一个 fused softmax：PyTorch eager → torch.compile → Triton；用 Nsight Compute 比较 DRAM bytes、occupancy、achieved bandwidth。

• 实现一个 block-scaled FP8/FP4 GEMM 的“概念版”或阅读 DeepGEMM 对应 kernel，写出 scale 粒度、accumulator dtype、dequant/fusion 的数据流。

□ 能从 profiler 看出一个 kernel 是被 memory、Tensor Core、special function unit 还是 launch overhead 限制。

阶段 7｜Data Parallel、ZeRO、FSDP2 与 Checkpoint

第 16–18 周掌握参数/梯度/optimizer state 的分片生命周期。
↑ 返回知识点目录

顺序

• PyTorch DDP：gradient bucket、autograd hook、AllReduce overlap。

• ZeRO-1/2/3：依次 shard optimizer / gradients / parameters；理解通信量与峰值内存。

• FSDP2：DTensor-based fully_shard；forward 前 all-gather、backward 后 reduce-scatter；resharding policy。

• Distributed Checkpoint：sharded state、异步 save、不同 world size 的 load-time reshard。

理论起点

论文 DistServe — prefill/decode 分离与 goodput。

论文 Splitwise — phase splitting 的另一代表工作。

□ 对齐退化前后的输入与服务目标，沿端到端关键路径找出首先变慢的区间，再选择通信、算子、存储或调度证据检验原因。

最终总项目：设计一个“百万上下文 Agentic MoE 平台”

不要选择多个 capstone。就做这一个：假设你要部署一个 1M context、MoE、原生 multimodal 的 Agent 服务，同时支持在线 inference 和持续 RL post-training。你可以用较小开源模型做实验，但设计必须按 frontier scale 写。

• 模型层：说明 attention/KV 方案（例如 GQA/MLA/sparse/linear hybrid）、MoE routing、precision、speculative decoding。

• 训练层：DP/TP/PP/CP/EP mesh、activation strategy、optimizer/precision、checkpoint、data path。

• 通信层：节点内/节点间 collective、EP all-to-all、GPU-initiated / RDMA 的候选路径。

• Serving 层：vLLM/SGLang engine，continuous batching、chunked prefill、prefix cache；是否 P/D 分离以及为什么。

• KV 层：HBM/DRAM/NVMe/remote pool 容量；KV-aware routing；压缩与持久化；cache admission/eviction。

• RL 层：rollout/trainer 是否 colocate，async queue、tool long-tail、weight transfer、staleness 控制。

• 平台层：Slurm/K8s、gang/topology scheduling、storage、observability、fault recovery、cost model。

• 评测：训练 tokens/s/MFU；推理 TTFT/TPOT/goodput；cache hit；network bytes/token；$/task；故障恢复时间。

论文与源码的统一阅读法

以后遇到任何新 AI Infra 技术，固定用下面七问，不要重新建立一套名词体系：

• 它在优化哪一个资源：FLOPs、HBM bytes、KV capacity、network bytes、latency、launch overhead、storage I/O？

• 瓶颈发生在训练还是 inference？prefill 还是 decode？短 context 还是长 context？dense 还是 MoE？

• 它把成本转移到哪里？例如 sparse attention 是否把成本转移给 indexer；P/D 是否把成本转移给 KV transfer；activation offload 是否把成本转移给 PCIe。

• 它依赖什么硬件假设：HBM/Tensor Core 比、NVLink domain、RDMA、FP4、TMA、symmetric memory？

• 它改变了 tensor layout / parallel mesh / scheduler 的哪一部分？

• 它的核心 benchmark 是否匹配真实 workload distribution 和 SLO，而不只是 microbenchmark？

• 如果换一代硬件（Hopper→Blackwell→Rubin，或 NVIDIA→AMD/TPU），这个优化还成立吗？
