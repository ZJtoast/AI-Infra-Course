一条请求的预填充与逐词元解码

假设分词器把提示词切成 A、B、C 三个 token，模型依次生成 D、E、F。服务收到请求时就知道 A、B、C，可以把它们一并送入模型。每层的因果掩码规定 A 只看 A，B 看 A、B，C 看 A、B、C。处理完这三行后，每层都留有三个位置的键和值（KV）。用最后一行 C 的输出给候选词打分，选出 D。这段处理已知提示的计算叫预填充（prefill）。

此时用户已经可以收到 D，但缓存里还没有 D 的那一行。下一次前向只输入 D，沿各层写入 D 的键和值，查询可以看 A 至 D，再从 D 的输出选出 E。普通自回归生成就这样用刚选出的 token 推出下一个，称为解码（decode）。E 的值要等处理 D 后才知道，因此同一条请求的这两个解码步有先后依赖。

本轮送入模型该层本轮结束时的 KV 位置新输出
预填充A、B、CA、B、CD
解码第 1 步DA、B、C、DE
解码第 2 步EA、B、C、D、EF

若请求生成三个 token 就结束，只需一次预填充和两次解码。假设客户端从发出请求开始计时，在第 80、105、137 毫秒分别收到 D、E、F。用户等第一个 token 用了 80 毫秒，这段时间包含排队、处理提示和传输。接下来两次等待分别是 25 毫秒和 32 毫秒。首个 token 等了多久、后续 token 来得有多快，可以从这三个到达时刻分别算出来。对照实现可阅读 Transformers 的逐步 KV 更新说明。

1　请求生命周期与计时边界

用户输入一段文本后，服务需要解析请求、按对话模板拼接消息、分词、准入与排队，再把 token 交给引擎。prefill 处理尚未计算的输入位置，生成首个输出 token；随后各轮 decode 处理已有输出并继续采样，直到停止条件满足。协议处理、模型执行和流式发送可以交叠，因此总耗时通常不能用几个随手采样的 CPU 函数时间相加得到。

沿图中的时间轴读一次请求。客户端在 0 秒发出请求，引擎在 0.10 秒接纳，在 0.30 秒首次调度，在 0.80 秒生成首个 token。客户端到 0.86 秒才收到它，又在 0.90 和 0.98 秒收到两个 token，在 1.02 秒收到结束标记。用户等待首个 token 用了 860 毫秒，后两次各等了 40 和 80 毫秒。从最后一个 token 到结束标记又过了 40 毫秒。

2　流式输出的首词元延迟、到达间隔与平均耗时

流式服务一边生成一边发送。客户端可以记录三种时间，分别是发出请求到第一个 token 到达的等待时间（TTFT），相邻两个 token 到达的间隔（ITL），以及首个 token 之后每个输出 token 的平均耗时（TPOT）。先看每条消息恰好带回一个 token 的情况。

以流式服务的一条完整记录为例。客户端在 0 ms 发出请求，在 70、90、140 ms 各收到一个输出 token。客户端 TTFT 为 70 ms，两个相邻输出间隔为 20、50 ms，整条请求的平均输出间隔为 140−703−1=35ms。若另有一个只输出一词的请求，它也有 TTFT，却没有任何后续间隔。把所有请求的间隔放在一起求平均时，长回答贡献的间隔较多。先算每条请求的 TPOT 再求平均时，每条有后续输出的请求各占一份。

每个输出 token 单独发送时，ITL 是相邻 token 到达时间之差；如果代理缓冲、推测解码或 stream 配置把多个 token 合成一条消息，客户端能直接测到的是消息间隔。vLLM benchmark 读取有效 stream chunk 时记录时间，后续使用实际输出 token 总数计算平均 TPOT，两者的样本单位因此可能不同。

3　分位数、均值与 SLO

服务水平目标（SLO）把“等得起”写成可检查的约定，例如“至少 95% 的请求在一秒内收到首个词”。先给每条请求算出首词耗时，从小到大排列，再检查有多少落在一秒以内。把所有人的等待时间加起来求平均，回答的是另一个问题。

一台服务同时处理长短两条请求。短请求 A 只留下一个 100 毫秒的间隔，长请求 B 有九个间隔，每个 10 毫秒。按请求平均，A 和 B 各占一半，把 100 和 10 相加再除以 2，得到 55 毫秒。按间隔平均，A 贡献 100 毫秒，B 贡献 90 毫秒，合计 190 毫秒分给十个间隔，得到 19 毫秒。

读者还会察觉偶尔的一次停顿。假设一个回答有 100 个间隔，其中 99 个各为 10 毫秒，总计 990 毫秒。加上一次 1000 毫秒的停顿，整段用时 1990 毫秒，平均只有 19.9 毫秒。若约定每次停顿都在 100 毫秒以内，就要检查这条请求的最长间隔，它在这里超出了 900 毫秒。

P99 是第 99 百分位数。以按排名取值为例，把 100 条请求的首词延迟从小到大排好，取第 99 个值。实际报表使用的分位数算法可能在相邻两个值之间插值。100个请求时尾部只有极少样本，重复运行的波动可能很大。求全局 P99 时，先合并各 worker 的样本或分布统计，再取分位数。求端到端 P99 时，先算每个请求的总时长，再对这些总时长取分位数。排队最久和 prefill 最慢的可能是两条请求。

SLO 还需明确单请求规则：TTFT≤500毫秒且TPOT≤30毫秒，或要求所有 ITL 都≤某阈值；不同规则的达标比例会不同。超时、取消、服务错误与无输出都应进入总请求统计。

把目标落实到一批请求上，例如给 100 条请求都设定首词延迟和后续平均耗时两道门槛。若其中 94 条同时达标、4 条首词过慢、2 条超时，这一批的达标率就是 94%。若服务约定至少 95% 达标，还差一条。

4　Prefill 与 decode 的权重复用

沿用 A、B、C 的例子。预填充时，线性层把同一张权重表用在三行提示上；刚生成 D 以后，下一步只把它用在 D 这一行上。若再加入两条也正等着出词的请求，一轮就有来自三条请求的三行，可以共用这张表。每个位置仍要单独乘加，把几行放在同一次矩阵乘里，内核就有机会从片上存储复用已经读入的权重。

权重矩阵 W 的形状为 [D,N]，本轮 Ntok 个 query token 形成 X:[Ntok,D]，输出[Ntok,N]，主要矩阵乘的浮点运算量约为2NtokDN FLOPs。每次乘加按两次浮点运算计。设每个权重元素占 p 字节，若 W 能在这一轮从 HBM 读取一次，权重字节为 DNp，则仅按权重项计算的算术强度为2Ntokp FLOP/byte。prefill 往往同时提供很多行；单请求常规 decode 只有一行，把多个请求放到同一轮可以增加 Ntok。

Flinear = 2NtokDN,    Iweight = 2Ntokp

设一个教学模型的线性层共有 70 亿个权重，每个 BF16 元素占 2 字节，全读一遍要搬 140 亿字节，即 14 GB。设显存带宽为每秒 2000 GB，读完至少要 0.007 秒，也就是 7 毫秒。一轮只生成一个 token 时，即便用满带宽，每秒也至多生成约 143 个。

再假设计算吞吐可达100 TFLOP/s，线性部分每个 token 约14 GFLOPs，则 batch 为 B 时每轮要算 B 份，每份 140 亿次运算除以每秒 100 万亿次，得到单份 0.14 毫秒，整轮的计算时间下界为0.14B 毫秒。它与7毫秒权重下界在B=50附近相交，说明继续增大 batch 可能使计算项成为约束。这是忽略 KV、通信、激活、低效 shape 和启动开销的教学交点；真实曲线需要测量，无法用峰值算式替代。

把本轮执行时间记作 Tstep，单位为秒。F 是本轮操作数，C 是每秒可执行的操作数；M 是本轮要搬的字节数，BW 是显存带宽，单位为字节每秒。两项相除都得到秒。即使计算与访存完全重叠，整轮也不能早于较慢的一项结束。

Tstep≥max(FC,MBW)

沿用上面的批量设定，令一轮 16 个请求各产一个 token，计算下界为 0.14×16=2.24 毫秒，权重读取下界为 7 毫秒。因此轮时至少 7 毫秒，对应吞吐至多 16/0.007≈2286 token/s。

M 应包含实际读取的权重、KV 与临时量，C 与 BW 也应使用对应精度和 shape 下的可达能力。decode 可能受 CPU 调度或 kernel 启动限制，大 batch decode 可能接近计算受限；长 prefill 也可能受 KV、特殊算子或跨卡通信限制。prefill/decode 描述输入形状，瓶颈由完整路径决定。

混合专家模型（MoE）里，每个 token 会被分给少数几个前馈网络，这些网络叫专家。若同一轮的两个 token 都交给专家甲，甲的权重可以用于两行输入。若它们分别交给甲和乙，就要访问两套权重，各算一行。看这类模型的访存，要按本轮实际用到的专家数和各自分到的行数来算。

两个请求同轮各解一码，线性层可让两行输入共用一次加载的权重。两者的历史 KV 若不共享，注意力仍要分别访问各自的历史。一条长请求混入后，权重复用行数几乎不变，KV 工作却可能显著增加。按 batch 大小分桶之外，同时记录各行上下文长度，才能把线性层收益与注意力压力拆开。

6　Decode 的 KV 读写

通常 prefill 最后一个输入位置的隐藏向量经输出投影和采样得到首个输出 token。该输出 token 尚未作为下一轮输入经过所有层；下一轮 decode 才为它生成 K/V 并写入缓存，再预测后一个 token。此时请求已经多了一个 token ID，但这个位置的 K/V 还未写入。调度器用 num_computed_tokens 单独记录已算到的位置。

先算一条新记录。用 L 表示层数，G 是每层的 KV 头数，d 是每头的键宽和值宽，p 是每个元素的字节数。例中有 8 个 KV 头，每头存一条键和一条值，各 128 个 BF16 元素，每个元素 2 字节。因此一层一位置占 4096 字节，32 层合计 131072 字节，即 128 KiB。

普通 GQA 的 KV 容量为2LGdp∑i=1BSi 字节，其中 Si 是第 i 个请求的历史长度、B 是请求数。沿用这组教学尺寸，L=32、G=8、d=128、BF16时，每个 token 跨层为128 KiB；单请求8192位置为1 GiB。16个同长度请求占16 GiB，每次全部推进一个 token 还增加2 MiB。长期常驻的容量、每轮新增写入与每轮历史读取需要分别核算。

上例的 16 个请求各有 8192 个位置。这一轮稠密注意力若把全部历史从显存各读一次，合计读 16 GiB，约 171.8 亿字节。沿用每秒 2 万亿字节的带宽，光读历史就要约 8.59 毫秒。若同一轮还从同一显存读 14 GB 权重，两笔流量要相加，至少用 15.59 毫秒。跨头复用、片上缓存命中和额外读取都会影响实测流量。

在保留全部历史的稠密自注意力中，每追加一个 token 都会增大有效 KV；分页分配的实际占用按页增长。滑动窗口可以限制保留长度，稀疏选择改变读取范围，MLA 与量化改变每条记录的大小，递归状态还会改变容量的增长形式。估算 decode 时间时，先确定该层使用的状态模型和实际读入的字节数。

7　KV 页表与物理页

为每个请求预留最大上下文会浪费大量空间；要求请求增长时始终维持一块连续内存，也可能触发搬运。分页将 KV 切成固定 token 数的页，每个请求保存逻辑页到物理页的映射。相邻逻辑页可以位于不同物理地址，attention 通过页表访问它们。分页首先解决空间管理与共享，dense attention 仍需读取全部有效历史。

从左边请求的第一个逻辑块出发，沿连线经过 Block Table，表项把它映射到右侧的物理块 7；第二个逻辑块落在物理块 1。每个块内的 token 顺序保持原样。追加 token 时可以从空闲池再取一块，读历史时则须按逻辑顺序查表，物理地址可以跳跃。

FlashInfer 是供推理引擎调用的 GPU 算子库。它把这一批请求的页号接成一张长列表，用三组数组标明每条请求占哪几项：indptr 长度B+1，给出每个请求在 indices 中的页列表区间；indices 保存物理页号；last_page_len 长度 B，记录每个请求最后一页的有效 token 数。它们只描述寻址与长度，KV 数值保存在独立张量中。非空请求的末页有效长度取1至 page_size，整页满时使用 page_size。

8　KV 尾页的空间与新位置的写入

引擎给请求追加一个词元时，要把这个位置的键和值写进缓存。缓存按页分配，假设一页能存四个位置。一条请求已存了三个位置，第四个词元可以写进原页，第五个才需要新页。如果两条请求各自独占尾页，引擎就得为第五个位置另分一页，即使另一条请求的尾页还有空位。下面把容量换成每页 16 项，沿两条请求分别计数。

页长为 16 时，31 个 token 用满第一页，在第二页占 15 格，余 1 格。33 个 token 用满两页，在第三页占 1 格，余 15 格。两个请求共占五页，80 格里有 64 格存了数据，剩下的 16 格分布在两个尾页。较大页通常减少页表项，却增加尾部浪费；较小页减少尾部浪费，却增加元数据和寻址工作，并可能不符合某些 kernel 支持的 layout。页大小需要与 kernel 和缓存共享粒度一起选择。

只有完整内容身份相同的前缀页才适合共享，引用计数决定何时可释放。若共享尾页还允许继续追加，两条分支写入不同 token 时需要分离存储或写时复制。容量计算既要数逻辑引用，也要数唯一物理页，实际分配量按去重后的页数计算。

9　连续批处理的逐轮调度

服务正在替 A、B 两人逐词生成回答，C 也发来了请求。静态批处理把 A、B 编为一组，等这组结束再处理 C。连续批处理则在每轮计算结束时重新组批。图中第二轮有空位，C 可以加入。到第三轮 B 已结束，C 在批内换了位置，引擎仍可用 C 的请求标识找到它原来的缓存。

Orca 把一次调度缩小到一轮模型执行。它把不同请求都要做的线性投影合成一次矩阵乘，又让各请求的注意力分别看自己的历史。这种按算子选择能合批哪些工作的做法称为 selective batching。

Orca：迭代级调度与selective batching

再看只有两个槽位的时间轴。A 还需2步，B 还需4步，C 等待且需2步，暂忽略 prefill 并假设每轮10毫秒。静态分组先运行A、B四轮，再运行 C 两轮，共60毫秒；逐轮补位让 C 在第3轮加入，与 B 一起在第4轮完成，共40毫秒。两者生成的有效 token 均为8个；实际轮耗时会随 batch 和历史长度变化，不能直接把这个比例当真实提速。

10　分块 prefill 对 decode 时延的影响

假设一轮最多算 4 个输入位置。老请求还要输入 1 个 token 才能出下一个词，新请求有 6 个提示 token。若这轮给老请求留 1 个位置，新提示就先处理前 3 个，下轮用已有 KV 接着处理后 3 个。两段仍属于同一次请求的预填充。若把预填充和解码放到不同 GPU 上，则还要把前一组卡算出的 KV 交给后一组，这个跨设备的过程在第十五课「分离式推理与 KV 传输」中展开。

一条长提示词若一次占满本轮计算预算，已开始输出的短请求就要更久才能拿到下一个词。将提示词拆开能让解码穿插进来，但块越小，重复调度的次数越多。比较方案时还要观察长请求自己的首词等待时间。

Sarathi-Serve 是一个采用分块预填充的推理服务系统。调度器让正在逐词输出的请求继续解码，再用一小段提示填充同一批次。例如开头例子中的 1 行解码和 3 行预填充可以一起做线性投影。下一轮继续为解码留位置，等长提示全部处理完，新请求也开始逐词输出。

例如10秒内完成100个请求，其中70个同时满足 TTFT 与 TPOT，goodput 为7 request/s。另一配置完成120个但只有60个达标，原始吞吐12 request/s 更高，goodput 却只有6 request/s。若额外有失败或超时，还需报告它们占全部发起请求的比例，以便将成功请求的时延与服务的失败率一并解读。

在稳定阶段记录服务能力时，需要说明观察窗口是否包含 warmup、发压后的排空，以及窗口开始前已在执行的请求。只统计一段中间输出峰值、却把请求完成数换成另一段数据，会破坏分母一致性。批量离线完成时间和在线持续服务容量也需要使用不同说明。

比较每卡吞吐时，把完成请求的速率除以参与这批服务的 GPU 总数。例如预填充用 2 张卡，解码用 4 张卡，两组一起每秒完成 60 条请求，则整套服务每卡平均每秒完成 10 条。

13　开环与闭环负载

设一个客户端发一条请求，收到完整回答才发下一条。服务每条用 100 毫秒时，它每秒能发 10 条。服务变成每条 200 毫秒，它就自然降到每秒 5 条。这种由完成时刻决定下一次发送的方式叫闭环压测，适合观察固定并发的用户会等多久。

若用户仍每隔 100 毫秒来一条，服务变慢后照样每秒来 10 条。假设服务器只能串行处理，每秒完成 5 条，待处理的请求就会每秒多出约 5 条。这种按事先给定的时刻发送请求的方式叫开环压测。用它测积压时，发压端也要有足够的连接把这些请求按时送出。

代码 14　vLLM 按 request_rate 与 burstiness 构造到达间隔

504 行把间隔分布的尺度设为速率和形状参数乘积的倒数。例如每秒计划 10 条请求，形状参数取 2，尺度就是 0.05 秒。两者相乘得到平均间隔 0.1 秒，单次实际抽到的间隔可以长也可以短。Gamma 分布的均值等于形状乘尺度，因此固定到达率后，改变形状可以改变突发程度，同时保持平均间隔。

无穷 request_rate 对应零等待，burstiness 无穷对应固定间隔；其他情况从 Gamma 分布采样，shape=1为指数间隔。该版本随后对有限固定速率的整段累计时间做归一化，使最终时间接近指定请求数/速率，因此不要把输出轨迹称为未经修改的独立 Poisson 样本。

同时设置有限的发送速率和最大并发数时会引入客户端信号量等待。到了计划到达时刻，客户端也可能尚未发出请求；只看 HTTP 发送后的 TTFT 会漏掉这段等待。当前 benchmark 将 client_queue_time 单独记录，分析过载时应把它与服务端队列一起检查。

request_func 在进入 semaphore 后才执行；输出 start_time 保留实际发送时刻，减计划到达时刻得到 client_queue_time。例如原定在 100 毫秒发出，直到 135 毫秒才取得发送名额，客户端排队便占了 35 毫秒。有限速率与并发上限同时使用时，实际服务端到达过程已经受到客户端反馈限制。

14　生成服务的延迟诊断

同一个模型处理两条请求，提示都长 4096 个 token，客户端都等了 0.8 秒看到首个输出，之后平均每 20 毫秒收到一个 token。长回答有 257 个 token，首个之后还要等 256 次，共 5.12 秒，加上首词等待，合计 5.92 秒。短回答只有 17 个 token，后面只等 16 次，共 0.32 秒，全程 1.12 秒。如果每次间隔缩短一半，长回答节省 2.56 秒，短回答只节省 0.16 秒。同样缩短 0.4 秒的首词等待，对短回答更划算。

同一请求若收到 n 个逐词包，端到端到末词的时长等于 TTFT 加后续 n−1 个实际间隔之和。这个闭合关系可查漏记录、错误分母或到达事件的归属。不同请求的 TTFT P99 与 TPOT P99 通常来自不同样本，不能将两个 P99 相加当作端到端 P99；应先对每条请求求总时间，再从其分布取分位数。

BF16
16 位浮点格式，使用 8 位指数和 7 位显式尾数。指数范围接近 FP32，小数有效位更少。
CUDA Graph
预先记录并实例化一组 GPU 操作及其依赖，再重放整个执行图，可减少主机逐次提交许多小操作的开销。
decode

FLOP
一次浮点算术运算的计数单位。按本节约定，乘法和加法各计一次；除以时间才得到吞吐量 FLOP/s。
FLOPs
一次给定运算所需的浮点操作总数。本课程通常将一次乘加计为两次操作，吞吐率另用 FLOP/s 表示。
GEMM
通用矩阵乘法。左矩阵的行与右矩阵的列逐项相乘、求和，得到输出的一个元素；训练和推理中的线性层大量使用这种运算。
GiB
二进制容量单位，1 GiB 等于 1,073,741,824 字节；1 GB 按十进制等于十亿字节。
GPU
图形处理器，使用大量线程并行处理数据。需要许多独立运算或数据复用时，它常比逐项在 CPU 上执行更合适。
GQA
分组查询注意力。多组查询头各自共享一组键和值，可以减少解码时需保存和读取的 KV 数据。
HBM
GPU 常用的高带宽显存，用于保存权重、激活和中间结果等数据。芯片与显存之间可持续传输的字节数会限制某些算子。
ITL
Inter-Token Latency，同一请求相邻两个输出词元抵达的时间间隔，可用来观察生成是否间歇性停顿。
JIT
即时编译。运行时根据实际输入或硬件生成可执行代码，首次编译费用与后续重复执行费用应分开报告。
key
注意力中用来与查询匹配的向量。每个可见位置提供一个键，其分数决定同位置的值参与汇总的权重。
KiB
二进制容量单位，1 KiB 等于 1,024 字节。
KV
键和值的合称。一个历史位置通常既提供参与匹配的键，也提供按注意力权重汇总的值。
logits
模型为词表中各个候选 token 输出的未归一化分数；经过 softmax 可得到概率。不同词表的同一数字编号不必指向同一 token。
MiB
二进制容量单位，1 MiB 等于 1,048,576 字节或 1,024 KiB。
MLA
多头潜在注意力。模型把历史内容压到低维潜向量，后续计算按模型规定从该向量获得各头所需的信息。
MLP
前馈网络，在每个位置的通道维上施加线性变换和非线性函数。常见解码器先扩展通道再投影回残差宽度。
MoE
混合专家模型。路由器给每个词元挑选少数几个专家，由选中的网络计算，再按路由权重合并结果。
P99
取同一类样本的第 99 百分位。求全局值时，将各组样本或能合并的分布统计汇总后再取分位数。
prefill
推理时处理已有提示词的阶段。模型可以同时计算多个输入位置，并留下后续生成要读的缓存。
QK
查询矩阵与键矩阵转置相乘，结果的行对应查询、列对应键。除以头维平方根等缩放可在乘法前或后实现。
query
注意力中发起查询的位置或它的向量。它与各个可见位置的键相乘，得到对应的一行分数。
shape
张量形状，按顺序列出每一维的长度。即使元素总数相同，批次轴与通道轴的互换也会改变算子的含义。
SLO
服务等级目标，例如规定一定比例的请求要在给定的首词时延内完成。计算有效吞吐量时要写明采用哪项目标。
stride
张量步长，指某一维下标增加一时，线性地址跨过的元素数或字节数。比较时须先确认单位。
token
分词器分配编号的基本单位，可能是一个字、词的一部分或标点。模型按编号查词嵌入表，生成时也按这些单位计数。
Top-K
按分数挑出最高的 K 项。排序稳定性、并列项和掩码会影响返回的下标，正确性检查需说明约定。
TPOT
Time Per Output Token，常用于表示首个输出之后平均每个词元的耗时。应注明是否排除首词以及使用了多少个生成间隔。
TTFT
Time To First Token，从请求的约定起点到看到第一个输出词元的时长。比较数据时应写明起点在客户端还是服务端。
value
注意力要汇总的内容向量。它与同位置的键配对，并按注意力权重计入输出。
信号
收发双方约定的完成标记。生产者更新标记前，要把标记与相应代的数据写入建立正确顺序。
准入
调度器确认有可用资源并允许请求开始执行。准入前的等待属于排队时间。
准入
开始服务新请求前，检查计算预算、缓存页和保留空间是否容纳得下这次及后续执行。
分块
把大矩阵按行列范围切成可由线程块协作处理的小矩阵，乘法沿归约维度逐块累加。
分数矩阵
一个头把每个查询与各个键分别点积后得到的矩阵。行对应查询位置，列对应键位置，完整存储的空间随两种位置数的乘积增长。
分桶
把若干实际批量映射到少量预先支持的形状。一条请求量为 3 的批次可选择容量为 4 的桶，空位需要正确屏蔽。
前缀命中
复用已经计算好的前缀 K/V。新增查询仍要读取掩码允许的前缀位置。
吞吐量
单位时间完成的工作量，例如每秒生成的词元数。比较吞吐量时，两次测量须统计同一种工作，并采用一致的起止条件。
因果掩码
限制一个位置只能访问自身和允许的过去位置，防止预测时读到未来内容。对角线的对齐方式取决于查询与键对应的绝对位置。
因果注意力
每个位置只使用自己及允许的更早位置，防止未来的信息泄漏到当前的预测中。
图捕获
把可表示的张量计算及依赖记录成图，以便编译器分析和生成内核。torch.compile 捕获张量计算及其依赖；CUDA Graph 捕获提交给设备的操作及其依赖。
在途
数据已开始传输，但相关读取、写入或完成通知尚未全部结束。缓冲区即使暂时没有计算在用，也不能随意覆盖。
复用
输入元素被加载到片上后，多次参加不同输出元素的乘加。估算节省量时应说明是哪一级存储少读了数据。
复用长度
可以复用已有计算结果的连续前缀长度。估算本轮开销时，应分别记录序列已推进的位置数和本轮还需计算的查询行数。
完整块
块内所有键对当前查询块中的每一行都可见，可省去逐元素的掩码判定。
工作区
算子在执行过程中为暂存中间数据而申请的区域。模型权重大小不变时，工作区仍可能随输入或算法改变。
布局
张量的逻辑坐标与物理存储地址之间的对应关系。相同形状的张量可能因步长不同而产生不同访存模式。
常驻
让已启动的工作单元在内核内部反复处理多个任务，而非处理完一块便退出。具体任务领取方式由程序决定。
引用计数
记录物理页或树节点仍被多少使用者持有，释放时还需考虑设备上的在途访问。
张量
按若干个轴排列的一组数。形状给出每个轴的长度，步长给出沿该轴移动一格时存储地址的变化。
归约
把一组数用求和、取最大值等操作合并成少量结果。算子内归约与跨卡归约面临不同的数据搬运和同步成本。
投影
此处指注意力与前馈层内的稠密矩阵乘。它按实际输入 token 行数重复执行，同一份权重可被多行共享。
排空
等待或确认已经提交的设备访问全部结束，使原缓冲能安全复用。
时间线
将不同线程、CUDA 流及设备活动按时间展开，可结合事件与请求编号追踪先后依赖。
显存
GPU 可直接访问的设备内存。讨论容量时要区分张量逻辑大小、分配器实际保留量与同时存活的峰值。
有效行
由一次实际路由产生的输入行。为满足对齐要求而补出的行也占空间，但不对应任何 token。
有效配对
对某个查询位置，掩码允许它读取的一个键位置。统计有效配对可估算算法工作量，实际内核还可能计算被掩掉的块内元素。
权重复用
一次加载的权重供多个输入行参加计算。在理想模型中，这会摊薄每行承担的权重读取字节数。
槽位
流水线中一块反复使用的缓冲区。同一地址先后保存多代数据，生产者要等上一个消费者用完才能覆盖。
激活
模型处理本次输入时产生的中间张量。它的形状和寿命依赖批量、序列长度以及接下来是否需要反向传播。
激活参数
MoE 在处理当前 token 时实际走到的参数。估算一次前向时要考虑专家选择，估算所有权重的常驻容量仍要计入未被本 token 选到的专家。
稳态
编译和一次性初始化已经完成、输入条件可重复时的执行状态；此时测得的单次节省可用于估算回本次数。
算术强度
以指定存储层次为边界，用浮点运算数除以跨过该层次的字节数，单位为 FLOP/B。
组合
把一个布局给出的坐标交给下一个布局继续映射。判断最终元素归属时，要按照两个映射实际作用的顺序计算。
融合
把原本分开的若干运算放到同一内核中执行，使中间值有机会直接从寄存器或共享内存传给下一步。
计时边界
明确一个耗时由哪两个事件的时间戳相减得到，跨主机相减前还须核对时钟关系。
请求轨迹
按同一个请求编号整理的排队、批次映射、计算、采样及缓存状态变化。
输出投影
拼接多个头的输出后再做一次线性变换，使同一位置可以混合来自不同头的特征。
递归状态
前一步计算留下的汇总量，读取后与当前输入一起形成下一步的状态。
逻辑位置
某个 token 在这条请求中的序列下标。它决定所查的旋转角，搬动保存该 token 的物理页不会改变这个下标。
量化
用有限个离散码近似表示原数值。尺度、零点和分组方式决定恢复后的数值及误差。
页
缓存分配器一次分配或回收的固定大小存储块。请求用页表把逻辑 token 的区间映射到这些块。
页表
把请求内的逻辑页号映射到物理缓存页号的索引结构，页内偏移另算。
页表
把逻辑位置所在的页映射到实际存储块的结构。在 KV 分页中，连续的逻辑位置未必位于连续的物理页。
预留空间
为已准入请求在完成前可能增长的 KV 留出的容量，不能把全部空闲页都再次承诺给新请求。
首 token 时延
从约定的请求起点到第一个有效输出 token 到达的时间，两端须采用同一计时边界。
驻留
线程块已获得在 SM 上运行所需的寄存器、共享内存和调度名额。块被接纳后，其线程仍可能等待数据。
