1　请求生命周期与计时边界

用户输入一段文本后，服务需要解析请求、按对话模板拼接消息、分词、准入与排队，再把 token 交给引擎。prefill 处理尚未计算的输入位置，生成首个输出 token；随后各轮 decode 处理已有输出并继续采样，直到停止条件满足。协议处理、模型执行和流式发送可以交叠，因此总耗时通常不能用几个随手采样的 CPU 函数时间相加得到。

设客户端在0秒发起请求，0.10秒引擎接纳，0.30秒首次调度，0.80秒生成首 token，0.86秒客户端收到首个有效输出；第二个输出在0.90秒到达，第三个在0.98秒到达，结束标记在1.02秒到达。客户端首输出延迟为0.86秒，两个消息间隔为40与80毫秒，最后输出延迟0.98秒，完整协议关闭延迟1.02秒。每个数字都有对应事件，不能统称“推理时间”。

TTFT（Time To First Token）必须说明起点在哪里、首个什么事件算输出。引擎内部可以从收到 token IDs 或加入队列开始；客户端通常从发送 HTTP 请求开始。TTFT 包含的分词、网络与排队范围不同，两套数值可以同时正确。单调时钟适合计算同一时钟域内的间隔，不能直接拿不同机器的 perf_counter 相减。

2　流式接口的 TTFT、ITL 与 TPOT

每个输出 token 单独发送时，ITL 是相邻 token 到达时间之差；如果代理缓冲、推测解码或 stream 配置把多个 token 合成一条消息，客户端能直接测到的是消息间隔。vLLM benchmark 读取有效 stream chunk 时记录时间，后续使用实际输出 token 总数计算平均 TPOT，两者的样本单位因此可能不同。

以流式服务的一条完整记录为例。客户端在 0 ms 发出请求，在 70、90、140 ms 各收到一个输出 token。若服务端另外记录了准入事件，需要先对齐时钟，才能把该事件画到同一条时间线上。客户端 TTFT 为 70 ms，两个相邻输出间隔为 20、50 ms，整条请求的平均输出间隔为 140−703−1=35ms。若另有一个只输出一词的请求，它也有 TTFT，却没有任何后续间隔。按请求求平均和把所有 token 间隔混合统计，长请求获得的权重不同。写出计时端点、首词是否算入和统计对象，才能解释两张时延图为何不同。

3　分位数、均值与 SLO

先计算每个请求首 token 之后各输出间隔的均值，得到各自的 TPOT，再对这些请求的 TPOT 求分位数；全局 ITL 则汇总所有间隔后统计，长输出请求贡献更多样本。假设请求 A 只有1个后续间隔100毫秒，请求 B 有9个间隔各10毫秒。两个请求 TPOT 的平均为55毫秒，而全部10个间隔的平均为19毫秒；它们回答不同问题。

TPOT 均值还会掩盖单次停顿。一个请求的100个间隔中99个为10毫秒、1个为1秒，平均 TPOT 为19.9毫秒，最大间隔却达到1秒。若产品要求持续流畅输出，就需要 ITL 尾部或每条请求最大停顿指标；仅满足平均 TPOT 阈值无法保证没有明显卡顿。

统一换成毫秒后，99 个短间隔一共 99×10=990 毫秒，那个长间隔贡献 1000 毫秒。总计 1990 毫秒除以 100 个间隔才是 19.9 毫秒。一个请求的最大停顿仍取单个最长间隔，即 1000 毫秒。

P99是给定样本集合上的99分位，计算方法和样本规模会影响值。100个请求时尾部只有极少样本，重复运行的波动可能很大。求全局 P99 时，先合并各 worker 的样本或分布统计，再取分位数。求端到端 P99 时，先算每个请求的总时长，再对这些总时长取分位数。排队最久和 prefill 最慢的可能是两条请求。

SLO 还需明确单请求规则：TTFT≤500毫秒且TPOT≤30毫秒，或要求所有 ITL 都≤某阈值；不同规则的达标比例会不同。超时、取消、服务错误与无输出都应进入总请求统计。

将每条请求折成一个平均间隔，再计算跨请求 P99，每条请求只投一票；将所有间隔平铺后求 P99，长输出请求可投许多票。二者分别回答“尾部请求的典型出词速度”和“尾部单次间隔有多长”。若 SLO 禁止任意一次超过上限，还要逐请求取最大间隔，不能用其均值替代。

情境　客户端逐 token 流式接收。A 发出两个输出词，相邻间隔 90 ms；B 发出四个，三个间隔均为 10 ms。两条请求均完整结束。另有 C 只收到一个输出词，无后续间隔，业务允许把它的 TPOT 记为缺失。

答案

4　Prefill 与 decode 的权重复用

对线性层 W:[D,N]，本轮 Ntok 个 query token 形成 X:[Ntok,D]，输出[Ntok,N]，主要矩阵乘的浮点运算量约为2NtokDN FLOPs。若 W 能在这一轮从 HBM 读取一次，权重字节为 DNp，则仅按权重项计算的算术强度为2Ntokp FLOP/byte。prefill 往往同时提供很多行；单请求常规 decode 只有一行，把多个请求放到同一轮可以增加 Ntok。

Flinear = 2NtokDN,    Iweight = 2Ntokp

以7B dense 参数、BF16权重为教学模型，权重共14 GB（十进制）。假设有效带宽2 TB/s 且每轮完整读取一次，权重读取下界为7毫秒。单请求每轮产1个 token，对应约143 token/s 上界；batch=16时若仍读一份权重、其他成本不变，则一轮产16个 token，对应约2286 token/s。每个请求的轮间延迟并没有因此缩短16倍。

再假设计算吞吐可达100 TFLOP/s，线性部分每个 token 约14 GFLOPs，则 batch 为 B 时计算时间下界为0.14B 毫秒。它与7毫秒权重下界在B=50附近相交，说明继续增大 batch 可能使计算项成为约束。这是忽略 KV、通信、激活、低效 shape 和启动开销的教学交点；真实曲线需要测量，无法用峰值算式替代。

把本轮执行时间记作 Tstep，单位为秒。F 是本轮操作数，C 是每秒可执行的操作数；M 是本轮要搬的字节数，W 是每秒可搬的字节数。两项相除都得到秒。即使计算与访存完全重叠，整轮也不能早于较慢的一项结束。

Tstep≥max(FC,MW)

沿用上面的批量设定，令一轮 16 个请求各产一个 token，计算下界为 0.14×16=2.24 毫秒，权重读取下界为 7 毫秒。因此轮时至少 7 毫秒，对应吞吐至多 16/0.007≈2286 token/s。

M 应包含实际读取的权重、KV 与临时量，C 与 W 也应使用对应精度和 shape 下的可达能力。decode 可能受 CPU 调度或 kernel 启动限制，大 batch decode 可能接近计算受限；长 prefill 也可能受 KV、特殊算子或跨卡通信限制。prefill/decode 描述输入形状，瓶颈由完整路径决定。

MoE 不能把所有专家总参数都算作每个 token 必读，也不能把单 token 激活参数乘 batch 后当成无复用流量。batch 中路由到的专家集合、专家权重缓存和每专家有效行数共同决定实际读取与 GEMM 效率，前面 MoE 课程的路由分布需要带入这里。

两个请求同轮各解一码，线性层可让两行输入共用一次加载的权重。两者的历史 KV 若不共享，注意力仍要分别访问各自的历史。一条长请求混入后，权重复用行数几乎不变，KV 工作却可能显著增加。按 batch 大小分桶之外，同时记录各行上下文长度，才能把线性层收益与注意力压力拆开。

5　前缀命中后的注意力计算

即使前 1000 个 token 全部命中缓存，第 1001 个位置的 query 仍须与可见的历史 key 打分。命中省去的是重建前缀各层 K、V 的工作；后缀对前缀的依赖仍然存在。

设已经缓存 P 个前缀 token，本次新增 Q 个 token。因果 attention 中第 i 个新增 query（i 从1开始）可读取P+i个 key，所以有效 query-key 配对数为QP+Q(Q+1)2。每对执行一次长度 d 的 QK 点积及一次 value 加权，按乘加计2 FLOPs，总核心约4Hd乘配对数。GQA 的 H 仍是 query head 数，KV head 共享主要改变存储和读取复用。

从新增位置的第一行数起，它能看见前缀的 P 个位置和自己。第 i 个新增位置能看见 P+i 个。把每一行的有效列数相加，前缀贡献一个长方形，新段内部贡献一个下三角。

∑i=1Q(P+i)=QP+Q(Q+1)2

Npairs = QP + Q(Q + 1)2,    Fattn ≈ 4HdNpairs

取P=4096、Q=256，有1081472个有效配对。若只算一个孤立256-token 序列，则为32896个；相差约32.88倍。前缀命中省去了旧 token 的投影、MLP 和旧 query attention，但新增 query 仍读取前缀 KV。对于长前缀短后缀，这部分访问可以成为主要成本。

配对数分两笔。256 个新查询各读 4096 个前缀位置，共 256×4096=1048576 对。新段内第一行只能读自己，最后一行能读 256 个，因此再加 256×257/2=32896 对；两项相加为 1,081,472。

分成多个 prefill chunk 不会减少这些满足因果掩码的 query-key 配对总数：每个 chunk 读取此前所有可见历史。它改变单轮工作量与调度机会，也可能增加权重重读和元数据准备次数。小 chunk 能限制一次占用时间，但吞吐损失与质量不相关；保持位置、mask 与 KV 追加正确时，数学函数保持相同，浮点归约仍可能产生小差异。

代码 4　完整前缀命中仍可能重算末尾，以获得 logits

这个版本把命中长度限制到prompt_length−1，并要求缓存命中块完整。若提示长度恰为块大小的倍数，可能重算末尾整块。不能根据“100%重复输入”推断本次完全没有 prefill 计算。

例如page=16，重复提示长度32时，最大命中长度31，完整块命中只能为16，余下16个 token 重算；长度33时，前32个可命中，剩1个重算。具体请求模式还可能主动禁用缓存读取，例如需要 prompt logprobs。评估缓存时，应分别记录复用的 token 数和本轮重新计算的 token 数。

用户的 prompt 全部 token 即使已有 KV，也未必留下能直接采样下一词的末行 logits。实现若只缓存完整页并要求用最后一个输入重算输出，逻辑上“文字相同”的命中量与实际少算的 query 数便不同。核对缓存报告时列出匹配长度、实际复用长度、本轮需执行的 query 区间，避免把完全相同的字符串记成零计算。

6　Decode 的 KV 读写

通常 prefill 最后一个输入位置的隐藏向量经输出投影和采样得到首个输出 token。该输出 token 尚未作为下一轮输入经过所有层；下一轮 decode 才为它生成 K/V 并写入缓存，再预测后一个 token。此时请求已经多了一个 token ID，但这个位置的 K/V 还未写入。调度器用 num_computed_tokens 单独记录已算到的位置。

普通 GQA 的 KV 容量为2LGdp∑i=1BSi 字节，其中 Si 是第 i 个请求的历史长度、B 是请求数。L=32、G=8、d=128、BF16时，每个 token 跨层为128 KiB；单请求8192位置为1 GiB。16个同长度请求占16 GiB，每次全部推进一个 token 还增加2 MiB。长期常驻的容量、每轮新增写入与每轮历史读取需要分别核算。

dense decode 理想情况下沿每个请求的全部历史归约。在上述16路8K 例子中，如果每个 KV 元素每轮读取一次，历史主流量约16 GiB；取有效2 TB/s，下界约8.59毫秒，已超过前节7毫秒权重下界。二者若竞争同一 HBM 带宽，合计字节下界约15.59毫秒，不能把两个独立时间下界简单取最大当作总带宽成本。实际缓存、融合和 KV head 复用会改变流量。

在保留全部历史的稠密自注意力中，每追加一个 token 都会增大有效 KV；分页分配的实际占用按页增长。滑动窗口可以限制保留长度，稀疏选择改变读取范围，MLA 与量化改变每条记录的大小，递归状态还会改变容量的增长形式。估算 decode 时间时，先确定该层使用的状态模型和实际读入的字节数。

若输入位置为 0、1、2，在位置 2 的输出 logits 上采出词 X，用户已看到第四个词，但目标 KV 当前仍只对应三个输入位置。下轮将 X 放入位置 3，才写出 X 的 K、V 并预测后续词。因此“生成长度”与“已计算长度”在这个边界相差一项。调度和缓存计数若不区分它们，常会从第二次 decode 起错一位。

7　KV 页表与物理页

为每个请求预留最大上下文会浪费大量空间；要求请求增长时始终维持一块连续内存，也可能触发搬运。分页将 KV 切成固定 token 数的页，每个请求保存逻辑页到物理页的映射。相邻逻辑页可以位于不同物理地址，attention 通过页表访问它们。分页首先解决空间管理与共享，dense attention 仍需读取全部有效历史。

从左边请求的第一个逻辑块出发，沿连线经过 Block Table，表项把它映射到右侧的物理块 7；第二个逻辑块落在物理块 1。每个块内的 token 顺序保持原样。追加 token 时可以从空闲池再取一块，读历史时则须按逻辑顺序查表，物理地址可以跳跃。

FlashInfer 使用类似 CSR 的三组数组描述一批请求：indptr 长度B+1，给出每个请求在 indices 中的页列表区间；indices 保存物理页号；last_page_len 长度 B，记录每个请求最后一页的有效 token 数。它们只描述寻址与长度，KV 数值保存在独立张量中。非空请求的末页有效长度取1至 page_size，整页满时使用 page_size。

9　连续批处理的逐轮调度

静态批处理先固定一组请求，通常等这一组全部结束才换下一组，短请求提前结束后，空位可能无法立即补入新请求。iteration-level scheduling 在每轮模型执行后检查完成、接纳和资源情况，让后续轮次的请求集合变化。Orca 将调度粒度推进到迭代，并通过 selective batching 处理不同算子的批处理需求；现代引擎在此基础上加入分页与混合 prefill。

Orca：迭代级调度与selective batching

10　分块 prefill 对 decode 时延的影响

一条长提示词若一次占满本轮计算预算，已开始输出的短请求就要更久才能拿到下一个词。将提示词拆开能让解码穿插进来，但块越小，重复调度的次数越多。比较方案时还要观察长请求自己的首词等待时间。

一段长 prefill 若在一轮调度中独占设备很久，已有 decode 请求必须等待这一轮结束才能继续输出。chunked prefill 把输入分段，允许每轮保留 decode 请求并混入有限 prefill 工作。Sarathi-Serve 围绕这种混合构造较均匀的迭代，改善吞吐与尾延迟之间的取舍。它没有消除 prefill 的计算量，只改变工作分配到各轮的方式。

11　计算与 KV 容量的准入限制

调度器即使还能计算更多 token，也可能已没有足够的 KV 页接纳新请求。调度器还需为新 query 写入的 KV、lookahead 和共享分支预留空间。权重、图捕获池、attention workspace 与其他常驻状态也占 HBM，留给 KV 的可用容量应从完整显存账中扣出。超出容量后的抢占与重算会额外消耗计算，导致并发提高却吞吐下降。

代码 11　只有 KV 槽位分配成功，本次请求才能继续被调度

allocate_slots 接收本轮 token 数和 lookahead 数量；返回非 None 才离开分配循环。分配失败后继续检查待释放块与抢占路径，因此 token 预算和 KV 分配构成两道不同约束。

当前代码的抢占路径还检查块能否立即释放：如果某请求的块仍被异步操作引用，逻辑上结束或移出运行队列也不能立即把那段存储交给新写入。通信完成、引用计数与 GPU 访问完成共同决定回收时刻。分布式 KV 课程会进一步追踪这类完成条件。

若可用 KV 容量为40 GiB，采用128 KiB/token 教学模型，总槽位上限为327680 token，忽略碎片时最多容纳40个8K 请求。若需要为每个请求再预留1K 输出，只能按9K 计，理论上限降为35个；实际还需考虑页取整、工作区和调度安全余量。未预留全部最大输出时，必须有后续增长失败的处理策略。

前缀缓存可以降低新请求的物理新增容量，但命中页可能被其他请求继续引用，不能任意回收；缓存的常驻空间也会挤占新请求。准入策略在收益与驻留成本间取舍，服务的命中率、重算率和排队长度应放在同一张时间线上分析。

12　吞吐量与达标吞吐量

以请求/秒计的吞吐量，分子是测量窗口内完成的请求数；output token/s 按实际生成 token 数计算；total token/s 还包括输入。长 prompt 可以显著推高 total token/s，即使首 token 延迟很差。每 GPU 吞吐需明确分母包含多少 GPU，以及是否包含 prefill 池、decode 池和其他服务设备。若分母只计解码卡，得到的是按解码卡数折算的吞吐量。计算整套服务的每卡吞吐时，还须计入其余参与服务的设备。

所有这些值使用 dur_s 作分母；good_completed 只计算满足所选 SLO 的请求。失败数单独报告，不能用成功请求吞吐掩盖失败比例。输入和输出分别计数，跨配置比较时必须保持定义一致。

代码 13　同一请求的各指标必须同时满足阈值才算 goodput

E2E 阈值先转换为秒，与 TTFT、TPOT 等一起加入 valid_metrics；zip 按请求配对，all 要求同时达标。分别计算 TTFT 达标率和 TPOT 达标率再相乘，通常无法得到联合达标率。

例如10秒内完成100个请求，其中70个同时满足 TTFT 与 TPOT，goodput 为7 request/s。另一配置完成120个但只有60个达标，原始吞吐12 request/s 更高，goodput 却只有6 request/s。若额外有失败或超时，还需报告它们占全部发起请求的比例，以便将成功请求的时延与服务的失败率一并解读。

在稳定阶段记录服务能力时，需要说明观察窗口是否包含 warmup、发压后的排空，以及窗口开始前已在执行的请求。只统计一段中间输出峰值、却把请求完成数换成另一段数据，会破坏分母一致性。批量离线完成时间和在线持续服务容量也需要使用不同说明。

一秒内完整服务 10 条请求，每条输入 100、输出 2，若输入也计入则为 1020 token/s，实际交付只有 20 输出 token/s。若其中仅 8 条同时满足质量与时延约束，goodput 为 8 个达标请求/s。同一份日志的三个数都成立，但抽样对象不同，应分别报告有效输出、完成请求、联合达标数及相同的实际观测时段。

13　开环与闭环负载

闭环压测中，服务变慢会让客户端更晚发出下一条请求，负载因此自行减轻。生产入口若继续按原速率接收请求，队列却会持续增长。开环测试把到达时刻独立于上一条请求的完成时刻，才能观察这段积压。

闭环固定并发，某请求完成后再补入下一个；服务变慢会自动降低发送速率，因此适合观察固定并发下的延迟和吞吐，却可能掩盖外部到达率不变时的积压。开环按独立时间过程发请求，能显示服务容量不足时队列增长，但发压客户端必须有足够连接、CPU 和网络能力。

代码 14　vLLM 按 request_rate 与 burstiness 构造到达间隔

504 行把间隔分布的尺度设为速率和形状参数乘积的倒数。Gamma 分布的均值等于形状乘尺度，因此固定到达率后，改变形状可以改变突发程度，同时保持平均间隔。

无穷 request_rate 对应零等待，burstiness 无穷对应固定间隔；其他情况从 Gamma 分布采样，shape=1为指数间隔。该版本随后对有限固定速率的整段累计时间做归一化，使最终时间接近指定请求数/速率，因此不要把输出轨迹称为未经修改的独立 Poisson 样本。

同时设置有限的发送速率和最大并发数时会引入客户端信号量等待。到了计划到达时刻，客户端也可能尚未发出请求；只看 HTTP 发送后的 TTFT 会漏掉这段等待。当前 benchmark 将 client_queue_time 单独记录，分析过载时应把它与服务端队列一起检查。

N¯ = λW¯

生产请求的长短分布与突发性会影响排队。即使平均输入输出长度相同，一组高度一致的短请求和一组少数极长请求混入的流量，也可能有不同 P99与缓存压力。压测至少保留输入长度、输出长度、前缀共享程度、到达时间和业务类型的联合关系。

一个闭环客户端始终等上一次请求完成后再发下一条。服务从 100 ms 变为 200 ms，忽略客户端间隔时，它自己把到达率从约 10s 降成 5s。服务端可能依然没有排队，看不出真实外部 10s 持续到来时会积压。开环测试必须比较计划发出与真实到达两份时间戳，尤其在发压端也受连接池限制时。

14　生成服务的延迟诊断

设单请求输入4096、输出257token，客户端 TTFT 为0.8秒，后续256个 token 间隔平均20毫秒。到最后输出的 E2E 为0.8+256×0.02=5.92秒；如果输出缩短到17token 而 TTFT 不变，E2E 为1.12秒。后一场景把 decode 提速一倍仅节省0.16秒，而将 TTFT 减少0.4秒更有影响。业务输出长度决定优化优先级。

先用现象缩小下一步需要查的对象

现象继续核对可检验的解释
客户端TTFT增加，引擎区间稳定client_queue、分词、网络、首chunk规则入口等待或输出缓冲改变
已有请求 ITL 出现周期性峰值每轮 prefill token数与执行跨度长chunk延长整轮时间
并发增大后吞吐下降KV 分配失败、抢占、重复prefill新增资源压力引入重算
同样 Top-K，长历史仍变慢indexer扫描、候选生成、页表准备主attention之外的成本随历史增长
大量 GPU 空隙CPU提交、同步、元数据与通信完成计算尚未拿到可执行输入

区分冷启动、warmup 与稳态：模型加载、JIT/autotune、CUDA Graph 捕获和首次页分配不应无说明地混入稳态延迟；但若业务频繁弹性启动，冷启动本身也有服务价值，应单独报告。重复请求会逐渐加热前缀缓存，比较配置前先固定缓存冷热条件。

评估记录应写明模型与分词器的版本、chat template、dtype、量化格式、并行布局、kernel/backend、采样和停止参数、真实输入输出长度、前缀命中、到达过程、失败率及计时边界。温度、stop 规则或 max_tokens 变化导致输出变短时，吞吐和延迟改善不能全部归因于系统实现。

本课的时延和吞吐量来自给定的教学数据。实际压测时，先用短请求核对计时边界，再提高到达率并观察队列是否持续增长。

同一请求若收到 n 个逐词包，端到端到末词的时长等于 TTFT 加后续 n−1 个实际间隔之和。这个闭合关系可查漏记录、错误分母或代理批量发送。不同请求的 TTFT P99 与 TPOT P99 通常来自不同样本，不能将两个 P99 相加当作端到端 P99；应先对每条请求求总时间，再从其分布取分位数。

本课术语
BF16
16 位浮点格式，使用 8 位指数和 7 位显式尾数。指数范围接近 FP32，小数有效位更少。
CUDA Graph
预先记录并实例化一组 GPU 操作及其依赖，再重放整个执行图，可减少主机逐次提交许多小操作的开销。
decode
推理时利用已有状态生成后续词元的阶段。普通自回归生成中，每条序列每轮通常新增一个位置。
FLOP
一次浮点算术运算的计数单位。按本节约定，乘法和加法各计一次；除以时间才得到吞吐量 FLOP/s。
FLOPs
一次给定运算所需的浮点操作总数。本课程通常将一次乘加计为两次操作，吞吐率另用 FLOP/s 表示。
GEMM
通用矩阵乘法。左矩阵的行与右矩阵的列逐项相乘、求和，得到输出的一个元素；训练和推理中的线性层大量使用这种运算。
GiB
二进制容量单位，1 GiB 等于 1,073,741,824 字节；1 GB 按十进制等于十亿字节。
GPU
图形处理器，使用大量线程并行处理数据。需要许多独立运算或数据复用时，它常比逐项在 CPU 上执行更合适。
GQA
分组查询注意力。多组查询头各自共享一组键和值，可以减少解码时需保存和读取的 KV 数据。
HBM
GPU 常用的高带宽显存，用于保存权重、激活和中间结果等数据。芯片与显存之间可持续传输的字节数会限制某些算子。
ITL
Inter-Token Latency，同一请求相邻两个输出词元抵达的时间间隔，可用来观察生成是否间歇性停顿。
JIT
即时编译。运行时根据实际输入或硬件生成可执行代码，首次编译费用与后续重复执行费用应分开报告。
key
注意力中用来与查询匹配的向量。每个可见位置提供一个键，其分数决定同位置的值参与汇总的权重。
KiB
二进制容量单位，1 KiB 等于 1,024 字节。
KV
键和值的合称。一个历史位置通常既提供参与匹配的键，也提供按注意力权重汇总的值。
logits
模型为词表中各个候选 token 输出的未归一化分数；经过 softmax 可得到概率。不同词表的同一数字编号不必指向同一 token。
MiB
二进制容量单位，1 MiB 等于 1,048,576 字节或 1,024 KiB。
MLA
多头潜在注意力。模型把历史内容压到低维潜向量，后续计算按模型规定从该向量获得各头所需的信息。
MLP
前馈网络，在每个位置的通道维上施加线性变换和非线性函数。常见解码器先扩展通道再投影回残差宽度。
MoE
混合专家模型。路由器给每个词元挑选少数几个专家，由选中的网络计算，再按路由权重合并结果。
P99
取同一类样本的第 99 百分位。求全局值时，将各组样本或能合并的分布统计汇总后再取分位数。
prefill
推理时处理已有提示词的阶段。模型可以同时计算多个输入位置，并留下后续生成要读的缓存。
QK
查询矩阵与键矩阵转置相乘，结果的行对应查询、列对应键。除以头维平方根等缩放可在乘法前或后实现。
query
注意力中发起查询的位置或它的向量。它与各个可见位置的键相乘，得到对应的一行分数。
shape
张量形状，按顺序列出每一维的长度。即使元素总数相同，批次轴与通道轴的互换也会改变算子的含义。
SLO
服务等级目标，例如规定一定比例的请求要在给定的首词时延内完成。计算有效吞吐量时要写明采用哪项目标。
stride
张量步长，指某一维下标增加一时，线性地址跨过的元素数或字节数。比较时须先确认单位。
token
分词器分配编号的基本单位，可能是一个字、词的一部分或标点。模型按编号查词嵌入表，生成时也按这些单位计数。
Top-K
按分数挑出最高的 K 项。排序稳定性、并列项和掩码会影响返回的下标，正确性检查需说明约定。
TPOT
Time Per Output Token，常用于表示首个输出之后平均每个词元的耗时。应注明是否排除首词以及使用了多少个生成间隔。
TTFT
Time To First Token，从请求的约定起点到看到第一个输出词元的时长。比较数据时应写明起点在客户端还是服务端。
value
注意力要汇总的内容向量。它与同位置的键配对，并按注意力权重计入输出。
信号
收发双方约定的完成标记。生产者更新标记前，要把标记与相应代的数据写入建立正确顺序。
准入
调度器确认有可用资源并允许请求开始执行。准入前的等待属于排队时间。
准入
开始服务新请求前，检查计算预算、缓存页和保留空间是否容纳得下这次及后续执行。
分块
把大矩阵按行列范围切成可由线程块协作处理的小矩阵，乘法沿归约维度逐块累加。
分数矩阵
一个头把每个查询与各个键分别点积后得到的矩阵。行对应查询位置，列对应键位置，完整存储的空间随两种位置数的乘积增长。
分桶
把若干实际批量映射到少量预先支持的形状。一条请求量为 3 的批次可选择容量为 4 的桶，空位需要正确屏蔽。
前缀命中
复用已经计算好的前缀 K/V。新增查询仍要读取掩码允许的前缀位置。
吞吐量
单位时间完成的工作量，例如每秒生成的词元数。比较吞吐量时，两次测量须统计同一种工作，并采用一致的起止条件。
因果掩码
限制一个位置只能访问自身和允许的过去位置，防止预测时读到未来内容。对角线的对齐方式取决于查询与键对应的绝对位置。
因果注意力
每个位置只使用自己及允许的更早位置，防止未来的信息泄漏到当前的预测中。
图捕获
把可表示的张量计算及依赖记录成图，以便编译器分析和生成内核。torch.compile 捕获张量计算及其依赖；CUDA Graph 捕获提交给设备的操作及其依赖。
在途
数据已开始传输，但相关读取、写入或完成通知尚未全部结束。缓冲区即使暂时没有计算在用，也不能随意覆盖。
复用
输入元素被加载到片上后，多次参加不同输出元素的乘加。估算节省量时应说明是哪一级存储少读了数据。
复用长度
可以复用已有计算结果的连续前缀长度。估算本轮开销时，应分别记录序列已推进的位置数和本轮还需计算的查询行数。
完整块
块内所有键对当前查询块中的每一行都可见，可省去逐元素的掩码判定。
工作区
算子在执行过程中为暂存中间数据而申请的区域。模型权重大小不变时，工作区仍可能随输入或算法改变。
布局
张量的逻辑坐标与物理存储地址之间的对应关系。相同形状的张量可能因步长不同而产生不同访存模式。
常驻
让已启动的工作单元在内核内部反复处理多个任务，而非处理完一块便退出。具体任务领取方式由程序决定。
引用计数
记录物理页或树节点仍被多少使用者持有，释放时还需考虑设备上的在途访问。
张量
按若干个轴排列的一组数。形状给出每个轴的长度，步长给出沿该轴移动一格时存储地址的变化。
归约
把一组数用求和、取最大值等操作合并成少量结果。算子内归约与跨卡归约面临不同的数据搬运和同步成本。
投影
此处指注意力与前馈层内的稠密矩阵乘。它按实际输入 token 行数重复执行，同一份权重可被多行共享。
排空
等待或确认已经提交的设备访问全部结束，使原缓冲能安全复用。
时间线
将不同线程、CUDA 流及设备活动按时间展开，可结合事件与请求编号追踪先后依赖。
显存
GPU 可直接访问的设备内存。讨论容量时要区分张量逻辑大小、分配器实际保留量与同时存活的峰值。
有效行
由一次实际路由产生的输入行。为满足对齐要求而补出的行也占空间，但不对应任何 token。
有效配对
对某个查询位置，掩码允许它读取的一个键位置。统计有效配对可估算算法工作量，实际内核还可能计算被掩掉的块内元素。
权重复用
一次加载的权重供多个输入行参加计算。在理想模型中，这会摊薄每行承担的权重读取字节数。
槽位
流水线中一块反复使用的缓冲区。同一地址先后保存多代数据，生产者要等上一个消费者用完才能覆盖。
激活
模型处理本次输入时产生的中间张量。它的形状和寿命依赖批量、序列长度以及接下来是否需要反向传播。
激活参数
MoE 在处理当前 token 时实际走到的参数。估算一次前向时要考虑专家选择，估算所有权重的常驻容量仍要计入未被本 token 选到的专家。
稳态
编译和一次性初始化已经完成、输入条件可重复时的执行状态；此时测得的单次节省可用于估算回本次数。
算术强度
以指定存储层次为边界，用浮点运算数除以跨过该层次的字节数，单位为 FLOP/B。
组合
把一个布局给出的坐标交给下一个布局继续映射。判断最终元素归属时，要按照两个映射实际作用的顺序计算。
融合
把原本分开的若干运算放到同一内核中执行，使中间值有机会直接从寄存器或共享内存传给下一步。
计时边界
明确一个耗时由哪两个事件的时间戳相减得到，跨主机相减前还须核对时钟关系。
请求轨迹
按同一个请求编号整理的排队、批次映射、计算、采样及缓存状态变化。
输出投影
拼接多个头的输出后再做一次线性变换，使同一位置可以混合来自不同头的特征。
递归状态
前一步计算留下的汇总量，读取后与当前输入一起形成下一步的状态。
逻辑位置
某个 token 在这条请求中的序列下标。它决定所查的旋转角，搬动保存该 token 的物理页不会改变这个下标。
量化
用有限个离散码近似表示原数值。尺度、零点和分组方式决定恢复后的数值及误差。
页
缓存分配器一次分配或回收的固定大小存储块。请求用页表把逻辑 token 的区间映射到这些块。
页表
把请求内的逻辑页号映射到物理缓存页号的索引结构，页内偏移另算。
页表
把逻辑位置所在的页映射到实际存储块的结构。在 KV 分页中，连续的逻辑位置未必位于连续的物理页。
预留空间
为已准入请求在完成前可能增长的 KV 留出的容量，不能把全部空闲页都再次承诺给新请求。
首 token 时延
从约定的请求起点到第一个有效输出 token 到达的时间，两端须采用同一计时边界。
驻留
线程块已获得在 SM 上运行所需的寄存器、共享内存和调度名额。块被接纳后，其线程仍可能等待数据。
